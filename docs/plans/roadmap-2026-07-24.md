# Shapewebs execution roadmap — 24 July 2026

## Objective

Deliver a distinctive, high-performance Shapewebs studio website and a secure
custom admin platform on Next.js, Better Auth, Neon, Drizzle, Vercel, and
Resend. Preserve the public/admin application boundary and do not expose a
self-service website builder.

## Starting evidence

- The public and admin apps build independently with webpack and Turbopack and
  retain the established Lighthouse budgets.
- Formatting, documentation, lint, types, dependency/cycle checks, coverage,
  boundaries, generation, audit, browser, accessibility, and Lighthouse gates
  are canonical root commands.
- The repository contains eight migrations plus disposable Neon migration,
  authorization, rollback, restore, and cleanup automation.
- Better Auth is mounted only in `apps/admin`; Google-only allowlisting, fixed
  sessions, TOTP step-up, audit events, and fail-closed authorization are
  implemented.
- The public lead path atomically persists Neon lead/outbox records. The admin
  worker, signed Resend webhook path, lead inbox, and owner-only settings read
  path are implemented behind server-only boundaries.
- Supabase remains transitional runtime code.
- Vercel Development has pooled least-privilege Neon runtime credentials;
  Preview and Production remain unchanged.
- Resend reports `shapewebs.com` verified in `eu-west-1`. A restricted staging
  key and webhook signing secret are stored only in the branch-scoped admin
  Preview environment. The enabled staging webhook passed a safe end-to-end
  `email.sent`/`email.delivered` exercise and a separate safe bounce/replay
  exercise with signed-event deduplication. Google Workspace now receives
  domain mail with Google MX, SPF, and DKIM; role aliases reach the licensed
  `admin@shapewebs.com` mailbox; DMARC remains at quarantine; and
  `noreply@shapewebs.com` remains a Resend-only sender. Production application
  configuration remains pending.
- Protected staging pull requests through `#15` have passed clean-runner
  checks and been merged. The foundation promotion pull request `#7` remains
  draft, and production remains on its known-good baseline.

## Non-negotiable architecture

- `apps/web` owns the static-first public site and untrusted public form entry
  points.
- `apps/admin` owns authentication, CMS, customer portal, email workers, and
  privileged integrations.
- `packages/database` owns Drizzle schemas, migrations, authorization context,
  and repositories.
- `packages/auth` owns Better Auth server configuration and authorization
  helpers.
- `packages/email` owns email templates, the Resend adapter, and
  provider-independent message contracts.
- `packages/ui` owns design tokens and reusable components.
- Global foundation CSS and CSS Modules remain the styling architecture.
- Public pages remain Server Components unless browser state is demonstrably
  required.
- Production and non-production data remain in separate Neon projects.
- Runtime roles never own application tables or bypass RLS.
- Business data is persisted before notifications are attempted.

## Execution order

### Milestone 0 — normalize and publish the foundation (complete)

Actions:

1. Review every changed and untracked path; resolve accidental duplicate files
   and remove generated clutter without touching ignored credentials.
2. Group the foundation into intentional commits:
   - baseline security, performance, and quality gates;
   - Neon/Drizzle/Better Auth package foundation and migrations;
   - documentation and provider runbooks.
3. Push `codex/foundation` and open a draft pull request.
4. Let GitHub Actions, OSV, Vercel previews, and repository rules run on a clean
   runner.
5. Fix failures without weakening budgets or security policies.

Exit gate:

- a reviewable draft pull request exists;
- the worktree contains no accidental duplicates or secrets;
- required checks pass on GitHub;
- the production domains still point to the known-good baseline.

### Milestone 1 — non-production lifecycle (complete and recurring)

Actions:

1. Create an ephemeral branch from the non-production Neon project.
2. Apply all committed migrations using the dedicated migrator.
3. Load deterministic synthetic fixtures.
4. Run the complete database authorization suite.
5. Exercise a migration failure and prove clean rollback.
6. Create a backup/export from synthetic data and restore it into another
   disposable branch.
7. Delete both branches and confirm production was never referenced.
8. Add the migrate/test/remove lifecycle to a protected GitHub Actions
   workflow.

Exit gate:

- migration, authorization, branch deletion, and restore evidence are recorded;
- no database owner or migration credential exists in Vercel;
- previews cannot inherit production data.

### Milestone 2 — secure Better Auth (code complete, staging pending)

Actions:

1. Mount Better Auth at `/api/auth/[...all]` inside `apps/admin`.
2. Add Google OAuth with exact localhost, fixed-staging, and production
   callbacks; never use wildcard preview callbacks.
3. Bootstrap the first owner from an explicit email allowlist.
4. Deny unassigned Google accounts without creating an application membership.
5. Add TOTP enrollment and a custom server-enforced OAuth-to-TOTP step-up for
   owner/editor sessions.
6. Re-authorize every Route Handler, Server Action, page loader, and mutation.
7. Add session revocation, audit events, rate limits, trusted-origin checks, and
   secure host-only cookies.
8. Add negative browser and database tests for anonymous, unassigned, expired,
   editor, owner, and cross-tenant personas.

Exit gate:

- an allowed owner reaches the minimal dashboard only after Google plus TOTP;
- unassigned and non-stepped-up sessions fail closed;
- no Supabase auth client is used by the verified path.

Required user input:

- user completion of phishing-resistant MFA for `admin@shapewebs.com`;
- Google Cloud Console availability for the newly provisioned Workspace
  organization.

### Milestone 3 — reliable email (code complete, staging partially verified)

Provider track:

1. Keep the verified `shapewebs.com` domain in `eu-west-1`, with sending
   enabled, receiving disabled, and tracking disabled.
2. Preserve the provider-generated SPF, DKIM, and Return-Path records alongside
   Google Workspace MX, SPF, and DKIM. Keep DMARC at quarantine until aggregate
   evidence confirms that both senders align.
3. Keep the restricted staging key only in `shapewebs-admin` Preview for Git
   branch `staging`.
4. Create a separate domain-restricted Production sending key only during the
   protected production-configuration milestone.

Code track:

1. Add a server-only `packages/email` package with typed message contracts,
   escaped HTML, plain-text output, and a Resend adapter.
2. Add a durable outbox with persisted attempt/lock state and deduplicated
   provider webhook events through reviewed Drizzle migrations.
3. Create outbox events in the same transaction as the lead or portal event.
4. Keep the Resend key only in `shapewebs-admin`; `apps/web` cannot send email.
5. Process pending events with database locking, bounded batches, exponential
   backoff, a terminal/manual-review state, and provider idempotency keys.
6. Use a `CRON_SECRET`-protected admin worker as the initial trigger; the next
   invocation retries persisted work because Vercel Cron itself does not retry.
   Hobby's once-daily schedule is development-only; provision minute-level
   scheduling before the 15-minute SLO becomes binding. Do not use a beta queue
   as the only durable copy of an email event.
7. Add a signed Resend webhook Route Handler. Deduplicate `svix-id` and tolerate
   out-of-order events.
8. Send minimal lead notifications containing a protected CMS link rather than
   the full message.
9. Test provider timeout, duplicate workers, invalid signatures, replayed
   webhooks, bounce/complaint states, API-key rotation, HTML escaping, plain
   text, and accessible template rendering.
10. Update the privacy notice and retention register for Resend processing.

Exit gate:

- a persisted lead survives provider failure;
- duplicate worker or webhook delivery cannot create duplicate mail or events;
- rotating/invalidating the key fails closed without losing the outbox event;
- delivery status is visible in admin operations.

Required user input:

- explicit authorization for controlled real-mail delivery tests;
- approval of any future DMARC change from quarantine to reject.

### Milestone 4 — replace transitional Supabase data paths (lead and settings

read paths complete; CMS/content paths pending)

Actions:

1. Implement Neon repositories for public content, leads, settings, previews,

2. Set transaction-local authorization context from verified sessions; never

Exit gate:

- `rg`, Knip, environment inventories, builds, and runtime tests show no
  Supabase consumer or secret;
- public forms and admin data paths use only the tested Neon roles.

### Milestone 7 — staging, security, and production launch

Actions:

1. Provision the separate production Neon project and recreate least-privilege
   roles through the reviewed bootstrap.
2. Configure fixed staging domains, Google callbacks, Resend keys/webhooks,
   Blob stores, Turnstile, and protected Vercel variables.
3. Run restore, rollback, ZAP, k6, browser, accessibility, authorization,
   email-delivery, and Lighthouse release suites.
4. Review CSP, cookies, logs, PII retention, provider access, alerts, and spend
   controls.
5. Deploy candidates without moving domains, smoke test them, then promote with
   Instant Rollback ready.
6. Verify Search Console, canonical URLs, sitemap, real-user Core Web Vitals,
   error alerts, and email delivery health.

Exit gate:

- production is promoted from a fully verified candidate;
- rollback and recovery are proven;
- no preview or staging environment can access production data.

updates, files, notification preferences, export, deletion, and support only
after the CMS and operational foundations are stable. Public signup remains
disabled until the full lifecycle and abuse model are tested.
